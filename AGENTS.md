# Code Structure and Where to Make Changes

Choose a module by responsibility, not by the call entry point or the location of an existing large file. Overall dependencies and ownership are described in [Layers and Compatibility](https://github.com/BMingSY/isaac-lan/blob/main/docs/layers-and-compatibility.md).

| Change area | Where to make the change | Boundary |
| --- | --- | --- |
| Automatic loading, startup assembly, component registration, and call order | [`src/app/`](https://github.com/BMingSY/isaac-lan/tree/main/src/app), [`src/bridge/app/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/app) | Compose existing components; do not put new gameplay rules here. |
| UDP, messages, fragmentation, compression, connections, and protocol | [`src/net/`](https://github.com/BMingSY/isaac-lan/tree/main/src/net) | Do not access game objects or identify Bosses, characters, or items. |
| State fields, capture/application, encoding, inventory, entity and grid consistency | [`src/bridge/sync/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/sync) | Own the generic synchronization contract; handle special gameplay through injected compatibility components. |
| Session progression, save/restore, floor-transition barriers, room and character lifecycle | [`src/runtime/`](https://github.com/BMingSY/isaac-lan/tree/main/src/runtime), [`src/bridge/runtime/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/runtime) | Coordinate execution timing and state invalidation; native object allocation and release belong to the backend. |
| Special rules for Bosses, items, characters, routes, and challenges | Corresponding categories in [`src/compat/{bosses,items,characters,routes,challenges}/`](https://github.com/BMingSY/isaac-lan/tree/main/src/compat) and [`src/bridge/compat/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/compat) | C++ strategies receive plain values; Lua adapters use game APIs and named native capabilities. |
| Detection, registration, integration, and unloading of third-party Mods | [`src/bridge/compat/mods/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/compat/mods) | Preserve source identification, real interface detection, and cleanup boundaries. Do not impose unnecessary version/source-hash restrictions, and do not modify upstream Mod source. |
| Public interfaces, actions, and lifecycle notifications for third parties | [`src/bridge/api/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/api) | Update the API contract and integration docs; do not expose native pointers or arbitrary memory access. |
| LAN bot control, observation, exploration, pathfinding, and hazard avoidance | [`src/bridge/lanbot.lua`](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/lanbot.lua), [`src/bridge/lanbot/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/lanbot) | Read existing views and synthesize normal input; do not change authoritative gameplay or synchronization rules. Acceptance fixtures belong in [`tests/`](https://github.com/BMingSY/isaac-lan/tree/main/tests) and [`tools/`](https://github.com/BMingSY/isaac-lan/tree/main/tools). |
| Menus, prediction, interpolation, camera, appearance, audio, and local presentation | [`src/presentation/`](https://github.com/BMingSY/isaac-lan/tree/main/src/presentation), [`src/bridge/presentation/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/presentation) | Do not decide authoritative damage, pickups, item effects, or room destinations. |
| Portable data rules independent of the game version | [`src/core/`](https://github.com/BMingSY/isaac-lan/tree/main/src/core) | Keep them runnable offline; do not introduce Hooks or game-memory layouts. |
| Native capability declarations, version detection, and game backend | [`src/engine/`](https://github.com/BMingSY/isaac-lan/tree/main/src/engine), [`src/engine/versions/<version>/`](https://github.com/BMingSY/isaac-lan/tree/main/src/engine/versions) | Keep ABI, layouts, native calls, Hooks, and object ownership within the version backend. |
| Runtime logs, diagnostics, and isolated frame capture | [`src/diagnostics/`](https://github.com/BMingSY/isaac-lan/tree/main/src/diagnostics) | Record evidence; do not make normal gameplay depend on diagnostic switches. |
| Offline regression, live-game fixtures, build/install/acceptance tools | [`tests/`](https://github.com/BMingSY/isaac-lan/tree/main/tests), [`tools/`](https://github.com/BMingSY/isaac-lan/tree/main/tools), [`cmake/`](https://github.com/BMingSY/isaac-lan/tree/main/cmake), [`package/`](https://github.com/BMingSY/isaac-lan/tree/main/package), [`.github/workflows/`](https://github.com/BMingSY/isaac-lan/tree/main/.github/workflows) | Follow the testing conventions below; tools must not become production gameplay dependencies. |
| Design, synchronization contracts, development, and verification docs | [`docs/`](https://github.com/BMingSY/isaac-lan/tree/main/docs); user instructions belong in `README.md` | Keep docs aligned with actual behavior and follow the review conventions below for public release copy. |

- Before fixing an issue, identify its responsibility: generic fields and state consistency belong in [`src/bridge/sync/`](https://github.com/BMingSY/isaac-lan/tree/main/src/bridge/sync); special rules for Bosses, items, characters, routes, and third-party Mods belong in their respective [`compat/`](https://github.com/BMingSY/isaac-lan/tree/main/src/compat) categories.
- [`app/`](https://github.com/BMingSY/isaac-lan/tree/main/src/app) assembles components and controls call order; [`runtime/`](https://github.com/BMingSY/isaac-lan/tree/main/src/runtime) owns session, room, and floor lifecycles; [`presentation/`](https://github.com/BMingSY/isaac-lan/tree/main/src/presentation) owns local display. Do not keep adding gameplay rules to assembly entry points.
- Prefer existing native interfaces and game Lua APIs. Avoid modifying [`engine/versions/`](https://github.com/BMingSY/isaac-lan/tree/main/src/engine/versions), network transport, Hooks, and native ownership code.
- If a native capability is genuinely missing, add the smallest named, scope-limited read/write interface or context management to the version backend. Gameplay matching, effect selection, and synchronization strategy still belong in upper layers.
- Document native changes in the relevant capability reference: interface limits, layout and ownership, and validation boundaries. Put the reason for the change and verification result in the PR or acceptance record, not in the design document.
- The network layer must not identify Bosses, characters, or items. Portable compatibility strategies must not read native memory or install Hooks.
- When adding a state field, update capture, application, schema, embedded-module manifest, and related docs together; verify the protocol version and extension fingerprint.
- Regression tests should cover the real trigger path, repeated state, cross-room/cross-floor behavior, and cleanup boundaries. Verify native behavior and visuals together according to the conventions below.

# Coding Conventions

- Follow `.editorconfig` and the existing formatters: four-space indentation for code and two spaces for YAML. Before committing, run `tools/format.py --check`; for PowerShell, run `tools/format_powershell.ps1 -Check`.
- PR titles must use a type prefix that matches the change, such as `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, or `chore:`.
- Split components by responsibility and state ownership, not mechanically by line count. Assembly entry points only connect components; shared implementations belong in common modules and must not be imported from a specific tool entry point.
- Each component initializes, invalidates, and clears its own state. Distinguish session, floor, view, and exit transactions; do not clear save protection prematurely before exit callbacks.
- Use named fields or shared field constants for cross-module data. Keep full display names in data tables, use named constants for enums, and avoid scattered numeric states or duplicated rule composition.
- Use named constants from the owning module for meaningful numbers (states, actions, field positions, thresholds, and native offsets). Reuse existing enums; values shared across languages must come from one source or be checked against the contract. Group native layout constants by object in the version backend rather than repeating offsets at call sites. Do not mechanically wrap obvious zero values, loop steps, or simple coordinates.
- Keep compact synchronized arrays under an explicit field contract. High-frequency capture may use ordered construction with field comments to avoid extra lookups and allocations. Pure refactors must verify that encoded bytes and restore order remain identical. When changing field layout, update the version, fingerprint, and consumers together.
- Keep game layouts, ABI, and Hooks in the version backend, connected to upper layers through named, scope-limited capabilities and synchronization callbacks. Reuse shared Lua ABI declarations and symbol loading; do not duplicate function signatures or expose arbitrary address access.
- Inject dependencies explicitly through parameters and keep module loading side-effect free. New components must update the embedded manifest, build registration, and layer checks.
- Extract repeated lifecycle, protocol, and test infrastructure while keeping each component's own rules. Avoid generic frameworks for extensions that do not exist yet.
- Tests should verify external behavior, contracts, and failure cleanup, not merely match implementation text or duplicate the implementation's own logic.

# Documentation Boundaries and In-Game UI

- Do not add anything to `README.md` without the user's explicit permission. Implementing a feature, fixing a bug, or the instruction to keep docs aligned with behavior does not grant that permission.
- Docs describe current facts. Lead with the conclusion and retain only necessary operations, contracts, and limitations. Design docs are not changelogs: do not include historical evolution, version-upgrade narratives, step-by-step fixes, debugging logs, test scores, or unimplemented proposals.
- Architecture/design docs explain only the current goal, module responsibilities, data flow, state ownership, lifecycle, key trade-offs, and limitations. Do not list every special case for individual items or Bosses, or accumulate native offsets, patch reasons, or PR history.
- Put API parameters, field layouts, native ABI, validation, and ownership in the relevant reference docs or source. Put specific effects and current compatibility status for characters, items, and Mods in their respective catalogs. Design docs should link to these sources instead of duplicating them.
- When revising a design, rewrite the relevant sections so they independently describe the final design. Do not append patch notes such as "added/fixed in version X" at the end. Remove obsolete or duplicate content while checking that required contracts and links remain; do not remove still-valid safety boundaries.
- Keep test procedures and default scope in the development/testing docs. Long-term acceptance results belong in `docs/history/`, organized by date and candidate build, with conclusions, scope, failures/unverified items, and evidence identifiers. Historical/evolution notes also belong only in that directory or in PR/commit records, never in design docs.
- Keep raw logs, screenshots, recordings, dumps, and large reports in test artifacts or CI attachments, not in the docs directory. Changing test scope must not rewrite old acceptance conclusions or hide known failures.
- Documentation review must check that it describes only the current design, contains no history or special-case details, does not duplicate other docs, and matches links and source code. Merely replacing words such as "added" or "fixed" while retaining a changelog structure is not sufficient.
- Links to project files/directories in docs must use this repository's GitHub `main` branch URL. Do not write local paths or links to uncommitted acceptance artifacts; use filenames, dates, rounds, or purpose labels instead.
- Keep only necessary names, controls, statuses, and error messages in the game UI. Put detailed explanations in `README.md` or `docs/`. Do not add unrequested prompts, menu explanation panels, or placeholder description fields.

# Release Copy Conventions

- Categorize release notes according to actual changes: "New Features", "Bug Fixes", and "Quality-of-Life Improvements". Omit a category when there is nothing relevant rather than inventing a feature.
- Base release notes on the actual changes between the previous published tag and the candidate commit. Summarize that entire range, not only the latest commit or PR.
- Show the complete proposed public copy for GitHub Releases, Steam Workshop descriptions, changelogs, and similar materials in the conversation for user review before publishing.
- Publish or update only after the user explicitly approves the displayed copy. A general request to "publish" or "release an update" does not approve text that has not yet been shown.
- Do not publish unapproved copy or bypass review by uploading a package or pushing a public repository. Local changes, packaging, and verification may be completed first.
- If approved copy changes later, request another review. Unchanged approved copy does not need repeated approval.
- Keep copy concise. Include only player-visible changes, core features, and necessary controls. Do not list failure causes, internal synchronization mechanisms, or step-by-step debugging. Unless requested, do not add testing suggestions, unverified compatibility claims, manual download links, or redundant instructions.
- Steam Workshop descriptions may include a link to the GitHub source.
- For Steam Workshop updates, reuse the [release process](https://github.com/BMingSY/isaac-lan/blob/main/docs/steam-workshop-release.md), the existing item, and approved copy; verify by downloading the published item afterward.

# Testing Conventions

- For routine development, debugging, and regression, default to tests that do not launch the game: offline Lua/Python, C++, protocol, and transport tests. When an issue is found, first add an offline reproducer where possible.
- Bug fixes, new requirements, and routine refactors should verify the change and its direct impact; every PR does not need the full live-game suite. Verify offline first where possible. For native behavior or visuals, complete code/build/offline checks, then verify the affected live-game scenarios together.
- Describe the change scope, selected checks, and results in the PR. Expand regression when the impact is uncertain. Development-specific tests and release acceptance are separate activities with separate records; do not rerun a development-specific suite just because the release scope includes related code, and do not use a local pass as a substitute for release-default coverage.
- Reuse a game process when checks can share one. Multiplayer scenarios start one host and one guest; reuse processes and the connection as much as possible. Clear fixtures and restore state between cases so they do not affect one another.
- Close/restart the game separately only when testing exit, restart, startup loading, or when the process cannot recover. Record the reason. Prefer handling session changes in the existing process when a restart is unnecessary.
- Existing live-game tools do not guarantee that all scenarios are automatically combined into one launch. Arrange scenarios according to the conventions above; do not repeatedly launch default groups as the routine test workflow.
- If the current task explicitly says not to launch the game, leave live-game verification as pending and do not launch it yourself. Passing offline tests does not mean live-game acceptance has passed.

# Pre-Release Acceptance Scope

Default release acceptance covers installation and basic multiplayer, every original Boss, ending routes, and normal-route progression. **It does not include item/character/Mod-specific tests, exhaustive item/card/pill traversal, or performance stress tests.**

Glitches, the D6, Genesis, Night Light, EID/Bag/Flow/alt-tab pause behavior, item/projectile stress, and input-response/camera checks are not part of the release checklist and are not automatically added just because the previous version had related changes. Fix these through targeted regression under the development-testing conventions. Add a release-specific test only when the user explicitly requests it.

- Identify the candidate commit and scope since the previous release. Run `python tools/test.py --profile full` for the Windows x86 build, network/native ABI tests, and package validation. Freeze the DLL, fixtures, and installer; record the commit and SHA-256.
- Use only isolated directories with ownership markers and separate ports for live-game acceptance. Before running, back up configuration, saves, and logs. Do not control the user's manually played instance. One coordinator schedules gameplay/Boss groups; groups may run in parallel, but multiple agents must not independently operate live game instances.
- Reuse host/guest processes and connections within each group; clear fixtures between cases. Real keyboard/menu checks require exclusive focus. Run performance-specific tests separately when needed. Record the reason for any required restart.

- Release records list only the checks performed for that release; reference development-specific results separately. Historical records preserve their original scope and conclusions; new rules must not delete old failures.
- Check host and guest assertions, logs, and required visuals together. For native Boss/transition/exit behavior, use the tool's `--heap-check` option to preserve anomaly evidence. Close the relevant instances normally, restore isolated data, and verify file hashes individually.
- Preserve original evidence after a failure and add an offline reproducer. After a fix, rebuild and rerun affected groups; expand the default regression when impact is uncertain. A case with only a start record, a missing peer result, a crash, or incomplete execution does not count as a pass. Record retests as a new round rather than overwriting the old failure.
- Add an acceptance summary to `docs/history/` with date, candidate and hash, actual scope, per-case results, restart reasons, and restoration results. Record performance data only when a performance-specific test was run. Distinguish fixed, still reproducible, intermittent/unlocated, and unverified issues; retain known issues outside the tested scope. Passing default checks must not be described as verification of every item or all performance behavior.
