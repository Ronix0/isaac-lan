# Room Rules

The character-selection lobby has a single-line **Room Rules** entry that shows a summary of the current options. It displays "None" when no rules are enabled, the rule's short name when one is enabled, or the first rule's short name plus the number of additional rules when several are enabled (for example, "FF +2"). Short names are supplied by each rule definition; they are not generated by truncating the full name.

The host can open the submenu and toggle each option independently with `[x]` / `[ ]`. Each change is synchronized immediately and clears everyone's ready state. The selection list remains open while toggling. Guests can open the same list to see live status but cannot edit it. The list shows six rules at a time; additional rules can be reached by scrolling with directional input or clicking the up/down arrows. **Back** stays fixed at the bottom. Returning to the lobby leaves the Room Rules entry selected.

Rules cannot be changed after a run starts. Normal mode and challenges without locked rules allow independent option selection. Options persist through saving, resuming, reconnecting, and restarting. If the saved rules differ from the current lobby, choose **Load Previous Rules**, ready up again, and continue. [Challenges with fixed rules](https://github.com/BMingSY/isaac-lan/blob/main/docs/lan-challenges.md) use their own defined option set. The Room Rules entry is disabled, and modification requests from both host and guests are rejected. Returning to normal mode allows editing again.

Whenever the host changes a checkbox, the options are saved in the `roomOptions` field of the local IP/port preferences file, `connection.txt`. They are loaded automatically the next time the host creates a room. If an older file does not contain this field, all options default to off. Lobby rules received by a guest are not written to local preferences. Saving the IP, port, and rules preserves the other fields. Writes use a temporary file replacement. If saving fails, the interface displays a notice, but the lobby selection already applied remains in effect.

## Shared Room-Clear Charge

Short name: **Charge**. Disabled by default. Whenever the original game grants charge for clearing a room, living online teammates share that progress, including teammates in other rooms. Players already handled by the original game are not granted it twice. Each separately cleared room contributes once. If the player who cleared the room already has a fully charged active item, other teammates can still receive the progress.

Normal rooms grant one charge unit as in the original game; large rooms grant two. Each recipient is processed according to their own active-item slot, charge type, and trinkets. Extra Battery slots are handled by the original charging method. Timed and special charge follow the original room-clear behavior. 4.5 Volt and Old Capacitor continue to prevent room-clear charge. Charge from battery pickups, taking damage, or dealing damage to enemies is not broadcast. Rewards such as flipping, healing, and drops are not extended to players in other rooms.

## Item Dice-Roll Allocation

Short name: **Dice Roll**. Disabled by default. After the original game confirms a pedestal pickup, every online, living, non-ghost player rolls D100 once. The highest result receives the item; ties are resolved randomly. Multiple bodies controlled by one player still count as one roll. The normal room rule does not add a Luck modifier. It allocates passive items and duplicate copies only; active items continue to use the original pickup and slot-swap behavior. First-pickup state and internal item data are preserved during allocation.

Purchase eligibility, costs, and choice groups remain controlled by the original game. Starting items, crafting, direct code grants, and state restoration do not trigger rolls. Chat displays pickup and roll results. Guests receive the already-settled inventory and do not roll again.

Challenge 1002, **Luck Game**, reuses the same allocation component while preserving the challenge's own Luck modifier, passive-pickup scope, floor-transition transfers, and extra rewards. The challenge's pickup strategy takes priority. Enabling this rule at the same time does not allocate an item twice or turn active-item pickups into rolls.

## Friendly Fire

Disabled by default. When enabled, tears, knives, lasers, and supported item effects owned by different players can damage teammates in the same room. Attack ownership is traced through the original spawner, parent entity, and familiar owner. Multiple bodies controlled by the same player do not damage each other. Ordinary body contact, enemies, and environmental attacks are not converted into friendly fire. The current supported item-effect scope is listed in the [Item and Effect Compatibility List](https://github.com/BMingSY/isaac-lan/blob/main/docs/item-effect-compatibility.md#pvp-item-effects).

Ordinary attacks are evaluated using their firing cadence and attack type. The attack entity's actual `CollisionDamage` is then converted into half-heart units. As output increases, the additional damage and fire-rate benefit becomes smaller. Rapid-fire and heavy attacks with the same theoretical output use the same curve. The conversion coefficient does not change with hit rate. Ordinary tears receive their coefficient when fired; delayed hits are not repriced. Critical hits and charge-shot multipliers are preserved but remain subject to the burst cap.

Spread shots fired by the same shooter in the same frame share one output calculation and one burst budget. Derived projectiles with a known parent attack inherit that budget. Familiars use their own firing cadence, initially with a conservative one-second interval, and learn shorter intervals from subsequent shots. Continuous lasers and knives check contact every two simulation updates. Lasers and held knives estimate output at that frequency; thrown knives use the owner's firing interval and preserve the damage from briefly passing through a target. Simultaneous attacks from the same source share output. When different attack streams are active at the same time, their estimated output is combined; a stream that stops firing becomes inactive. A continuous contact from a piercing tear is counted only once.

Effective damage below half a heart accumulates on the same target. After each settlement, the fractional remainder is retained. Ordinary hits in the same simulation update are merged into one original `TakeDamage` call, so original damage reduction, shields, damage callbacks, and death handling still apply. Only the ordinary hit cooldown that this component confirms it has applied can be temporarily suspended during the next PvP query/settlement window, then restored. Environmental hit protection, shield absorption, item invulnerability, and additional original protection are not shortened. Original hit reactions and protection against environmental damage remain under game control.

The damage cap for one attack or a group of ordinary hits in the same frame is half of the target's maximum effective health, rounded down to half-heart units, with a minimum of half a heart. Values after the original floor damage modifier are also subject to this cap. Red-heart capacity uses the current maximum container count. Soul Heart and Bone Heart capacity uses the capacity observed in the room, so the protection cap does not shrink as health is lost. When the actual loss from one hit or same-frame group is at least one heart, the target receives ten simulation updates (about one third of a second) of PvP protection, blocking attacks from every other player. A player with very little health can still be defeated. Damage beyond the burst budget, contact during protection, and damage blocked by shields or callbacks do not create deferred damage.

Explosions and recognized original item landing damage retain the original player-damage units and source flags. They use the same per-attack budget and short protection. Explosion damage against monsters is not passed through the tear conversion. The callback receives damage already modified by the original game; forwarding it uses `DAMAGE_NO_MODIFIERS` to avoid applying reductions or floor bonuses twice. Shields and invulnerability are still respected. When Friendly Fire is disabled, damage with a clear other-player owner is cancelled; self-damage and environmental damage without a player owner are unaffected.

Room-wide damage and continuous item effects use item-adapter components to select targets, then submit each hit to the same fractional-damage settlement path. Related callbacks from one use share a budget. Player damage already produced by the original game has only its ownership and cap managed; it is not applied a second time. Targeting adapters preserve the original effect entities and presentation, using use records to constrain source and lifetime.

A gap of more than one second between continuous hits discards the fractional remainder. Leaving a room, replacing a body, disconnecting, changing floors, rewinding time, disabling the rule, or invalidating the session clears the corresponding attack, remainder, and cooldown ownership. Ignored contacts are not replayed after protection ends.

## Special Room Gather

Short name: **Gather**. Disabled by default. When any online player enters an original special room, other online players are automatically teleported to the same room and dimension. This covers all original special room types, including Boss, Shop, Treasure, Secret, Angel/Devil, and Error Rooms. The actual room type is used for detection: ordinary red rooms do not trigger gathering, but Ultra Secret Rooms do. Entering through a door, card, or `/tp` also applies. No additional room is generated.

Gathering uses the position of a teammate already in the destination room as the landing point. The Basement retains that room's return entrance. Players already in the destination room do not move, and arrival from a gather does not trigger another gather. Players can leave freely afterward; entering a special room again can trigger a new gather. If several players are observed entering different special rooms in the same round, the lowest player slot determines one gather. Arrivals while a gather is in progress do not start another round. Offline players are excluded. Positions restored by resuming, reconnecting, or changing floors are treated only as initial records.

This rule reuses the native room-transition interface used by `/tp`. The existing room system handles all character bodies, familiars, and room-entry effects. If the initiator leaves, the connection becomes invalid, or the wait times out, requests that have not yet executed are cancelled. Run/floor transitions discard old records.

## Gather in Every Room

Short name: **Gather Everywhere**. Disabled by default. Whenever an online player changes rooms, every other online player is automatically teleported to the same room and dimension, landing near the initiating player at a walkable position. This applies to normal rooms, ordinary red rooms, and special rooms. Returning from a special room to a normal room also triggers it. Doors, cards, and `/tp` use the same rule. Players already in the destination room do not move.

Arrival does not trigger another gather. If the initiator or an already-arrived teammate changes rooms before the current gather completes, pending requests for the old destination are cancelled and the gather is redirected to the new destination. Teammates who are still transitioning keep the current gather target. If several players are observed changing rooms in the same round, the lowest player slot determines one gather. When **Special Room Gather** is also enabled, only this rule runs; players are not teleported twice.

Offline players are excluded. Positions restored at run start, on resume, after reconnecting, or after a floor change are used only as initial records; later room changes continue to trigger gathering. Connection invalidation, timeout, disabling the rule, or session invalidation clears pending requests. Requests from an old run or floor cannot affect the new state. If there is no walkable position nearby, the original room-entry landing position is retained.

## State and Responsibilities

Option definitions come from [core/room_options.h](https://github.com/BMingSY/isaac-lan/blob/main/src/core/room_options.h). The runtime validates them and exports their bit values, names, and `shortName` values. The menu uses these to build the summary and checkbox rows. The challenge catalog's `roomOptionsLocked` field is exported to the menu through `net_challenges`. The runtime also validates the fixed option set and rejects changes when options are locked. The network transmits only `RunRules.options`; it does not interpret gameplay behavior. Save data and personal completion-mark lifecycles are described in [Session and State Recovery](https://github.com/BMingSY/isaac-lan/blob/main/docs/session-lifecycle.md).

[room_rules.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/runtime/room_rules.lua) manages optional effects by session and world generation. Unsettled events are cleared when their context becomes invalid. [clear_charge.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/clear_charge.lua) collects original room-clear notifications and grants charge after the room simulation scope exits. [loot_roll.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/loot_roll.lua) handles player grouping, dice ordering, and one-time inventory allocation; challenges provide their own Luck strategy. Both rules reuse the original active-charge and inventory synchronization paths and do not extend the message layout.

[friendly_fire.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/friendly_fire.lua) checks attack contacts in every occupied room during host simulation, then calls the original damage interface. Guests continue to use existing health, character-action, and damage-state synchronization. Contact and fractional damage are owned by this component. [pvp_attacks.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/pvp_attacks.lua) manages firing records and per-attack budgets; [pvp_health.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/pvp_health.lua) manages original cooldown ownership and short protection; [pvp_damage.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/pvp_damage.lua) defines the pure numeric curve. [compat/items/pvp.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/items/pvp.lua) owns item-use, targeting, room-entry, and continuous-effect state. Use callbacks are connected by the assembly layer. This temporary state is not written to personal saves. Shared swept-circle collision is implemented in [core/contacts.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/core/contacts.lua); the same geometry function is also used by local hit prediction.

[room_gather.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/rules/room_gather.lua) observes accepted player positions outside the room-simulation scope. It applies the selected room-type restrictions or accepts every room change, starts a single gather, and consumes arrival events. [room_placement.lua](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/runtime/room_placement.lua) provides shared safe-landing calculations for player-target teleports and Gather Everywhere, handling all bodies belonging to the same player. Position records and unfinished gathers are cleared by `room_rules` when the session or world generation changes. Rule bits reuse `RunRules.options`; teleport results reuse existing room synchronization. No message or state-field layout is extended, and the extension fingerprint distinguishes different implementations.
