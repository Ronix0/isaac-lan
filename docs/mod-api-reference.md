# Mod API 2 Reference

The entry point is `IsaacLAN.API_VERSION == 2`. Call all handle and action methods with colon syntax. The SDK factory is `SDK.attach(mod, id)`. See the [Quick Start](https://github.com/BMingSY/isaac-lan/blob/main/docs/third-party-mod-integration.md) for integration.

## Attachment and Lifecycle

`IsaacLAN:Attach(mod, id)` attaches the instance returned by `RegisterMod`. `id` is a namespace shared by all clients. It may contain only ASCII letters, digits, `_`, `.`, and `-`, and must be 1–64 bytes long. Attaching the same instance and ID again returns the same handle. A different instance with the same name, or the same instance with a different ID, throws an error. A handle can be attached again after it is closed.

| Handle method | Contract |
| --- | --- |
| `IsAttached()` | Whether the handle is still open |
| `IsActive()` | Whether a LAN game is in progress, including view preparation. Returns `false` in the lobby and ending phases; single-player fallback is still prohibited there. |
| `IsReady()` | Whether the local view can currently be read. LAN requires the current generation to have been committed; single-player requires a character to exist. |
| `IsAuthority()` | Host in an active LAN game, or single-player. Returns `false` in the lobby, ending phase, or after close. |
| `View()` | Copy of the local view; `nil` when not ready |
| `GetLocalPlayers()` | Array of locally controlled characters, including both bodies; empty when not ready |
| `GetOwnerId(player)` | Stable participant ID, starting at 1; `nil` for an unknown object |
| `GetPlayerId(player)` | Current logical body ID, such as `p2:1`; `nil` for an unknown object |
| `IsLocalPlayer(player)` | Whether the character belongs to a local participant |
| `GetLocalRoom()` | LAN `{runId, worldEpoch, index, dimension}`; `nil` in single-player or when not ready |
| `WithLocalView(fn)` | Runs a read operation in the local room and local character list, preserving all return values; when not ready, returns `nil, "view_not_ready"` |
| `OnLocalRender(fn)` | Calls `fn(view)` on each available render frame and returns a repeatable cancellation function |
| `On(event, fn)` | Subscribes to LAN lifecycle events and returns a cancellation function; no events are emitted when LAN is inactive |
| `Action(name, definition?)` | Defines or retrieves an action object; see below |
| `Close()` | Removes owned render callbacks, subscriptions, actions, and registrations; can be called repeatedly |

Common `View()` fields are `players`, `ownerId`, `networked`, and `tick`. In single-player, `tick` is the game-frame count and all local bodies belong to participant 1. LAN views also include `runId`, `worldEpoch`, `revision`, `room`, and `playerSignature`:

| LAN field | Purpose |
| --- | --- |
| `runId` | Run identity generated by the host; invalidated when a new run starts |
| `worldEpoch` | World generation; invalidated by floor changes, Hourglass, R Key, and other rebuilds |
| `tick` | Authoritative simulation tick, not the local render frame |
| `revision` | Local view commit sequence, starting at 1 after rebuild; not comparable across clients |
| `room` | Room identity; dimension and index together determine the location |
| `playerSignature` | Opaque marker for changes to the character set, objects, or types; compare as an opaque value |

Identity is not derived from temporary display order, controller number, or entity address. Reconnecting retains the participant slot. After a body is replaced, retrieve the object again. Cross-world caches should include `runId` and `worldEpoch`. Arrays and tables are copies, but entity objects still refer to native game objects and should not be retained across resets. Identity queries can also recognize registered remote bodies, but do not add teammates to the local-player array.

`WithLocalView` supports nesting and exception recovery. It changes the read scope only for the duration of the wrapped call and does not clear the Mod's own caches. Do not change the world, consume random sequences, or suspend across frames inside it. `OnLocalRender` automatically wraps this scope; render frequency is not tied to network commit frequency. A callback error is logged and disables only that callback, not other Mods.

| LAN event | Trigger |
| --- | --- |
| `StateReset` | Old view has been cleared before exit/rebuild; arguments contain the old context and `reason`. Clear caches only. |
| `LocalPlayersChanged` | Local body set, objects, or character types change |
| `LocalRoomChanged` | Local room or dimension changes; a teammate changing rooms alone does not trigger it |
| `ViewUpdated` | A complete local view has been committed |
| `SessionReady` | First view is ready, or the first view after a rebuild is ready |

Events run on the game main thread, after complete state application and native-scope restoration, and before UI drawing. Required events run in the order shown. Except for `StateReset`, callbacks execute in the local read-only view. Event arguments are copies of the committed context; use `lan:View()` to retrieve characters. Events are not replayed for subscriptions added later. `SessionReady` may occur multiple times in one run. A subscription error disables only that subscription. During `StateReset`, do not use old objects to access the world.

## Actions and Completion Results

`lan:Action(name, definition)` creates an action object. `lan:Action(name)` retrieves an existing action or creates a version-1 remote reference. Supplying a definition again for the same name throws an error. To specify a version for a remote reference, pass `{version = n}`; it does not provide a local handler. Names must be 1–32 bytes and use the same character restrictions as integration IDs.

| Definition field | Contract |
| --- | --- |
| `version` | Action business-contract version; defaults to 1 and must be an integer from 1–65535. Requesting client and host must match exactly. |
| `validate(payload)` | Validates payload structure only and must return `true`. By default, only `nil` is accepted. |
| `execute(context, payload)` | Executed only by the host in LAN; used as the default implementation in single-player. Returns the final result or an asynchronous LAN operation. |
| `solo(context, payload)` | Optional single-player override for `execute`; must return the final result synchronously. |
| `cooldownTicks` | Host rate limit per action and participant; defaults to 15 and ranges from 1–1800. Single-player business logic manages its own rate limit. |

The action version describes the request/result structure and is independent of the Mod release version and network protocol. A UI Mod does not need to lock to an upstream version or source hash. The host publishes available actions. `action:IsAvailable()` is true only when the current version matches and the handle is ready. An action is unavailable after close.

`action:Request(payload?, {player?, onResult?}?)` always returns a request object: `{status, id?, code?, result?}`. The initial `status` is `pending`; when complete, the final status and `result` are set. If `player` is omitted, the first local body is selected. A specified body must belong to the local participant. LAN requests carry only a stable character ID; the host checks participant ownership again from the connection and resolves the entity. Another player's body cannot be selected.

`onResult(result)` is called at most once and receives `{status, code, data?}`. A committed LAN request also includes `requestId`, `runId`, and `worldEpoch`. Local rejection and single-player execution may complete synchronously; do not assume the callback runs after `Request` returns. Host business data belongs in `data`. Closing an action/handle notifies pending requests with `unknown/integration_closed`. A late receipt does not notify again and does not mean host execution was rolled back.

| Final status | Meaning |
| --- | --- |
| `applied` | Authoritative operation completed, such as actually reaching the destination |
| `rejected` | Validation or conditions failed; no operation was executed |
| `cancelled` | Operation ended because of disable/reset or similar; any cost already incurred is not automatically reversed |
| `unknown` | Timeout, disconnect, or exception prevented confirmation of the complete result; inspect authoritative state and do not automatically retry with a new ID |

Host-originated requests also pass through the queue and deduplication. The host calls the handler in the authoritative room of the initiating participant. `context` includes `player`, `playerId`, `ownerId`, `room`, `runId`, `worldEpoch`, and `requestId`. Single-player supplies only local-view fields and the selected character identity. `validate` checks structure only; `execute` must check live permissions, costs, paths, room-clearing requirements, and other conditions. If a handler throws, the result is `unknown/handler_error` and that host handler is disabled. Writes that already occurred are not rolled back.

### Asynchronous Operations and Movement

`context:Wait({poll, cancel?})` creates an operation only within the current host handler. It is scheduled after `execute` returns. `poll()` runs in the participant's current room and returns `nil` to keep waiting, or `{status, code, data?}` to finish. `cancel()` is a cleanup function that may run on success, failure, timeout, disable, or world reset. It should tolerate repeated cleanup and must not depend on an old room scope. Maximum wait: 5 seconds.

`context:MoveTo({index, dimension})` can submit a participant transition from the current handler or its active operation. It returns an asynchronous operation or `nil, code`. Index -20–168 and dimension 0–2 are only parameter ranges; Mod logic must validate whether the destination exists, can be entered, and has a valid route and cost. Completion is `applied/arrived` only when the actual position matches. If the character has not arrived within 3 seconds, the result is `unknown/arrival_unconfirmed`. The action targets the selected body, but room movement applies to the participant as a whole. A participant who has arrived is not sent back to the source. Do not modify the target table before completion.

These methods are available only in LAN-authority action contexts. Provide `solo` for independent single-player behavior and call the original single-player logic. A context is not a long-lived permission object and must not be retained for use in another callback.

### Transport Boundaries and Errors

Requests and results use reliable, ordered control messages over ENet UDP. Identity is bound to the connection, and source room/world generation are checked before execution. Supported data types are booleans, finite numbers, strings, contiguous arrays, and tables with string keys only. Functions, entities, metatables, and cyclic references are rejected. The complete message, including its header, is limited to 2048 bytes; strings to 512 bytes; keys to 64 bytes; total table entries to 128; and nesting depth to 6. A request that cannot be encoded is `rejected/invalid_payload`. A result that cannot be encoded is `unknown/invalid_result_data`; it does not silently disappear and wait for a timeout.

A Lua environment can register at most 16 handlers, including built-ins. The submitting side can have at most 8 pending requests. The host can queue at most 8 actions per participant and run 1 asynchronous operation at a time. Transport caches at most 32 extension messages per sender and 64 per second. A request that is not acknowledged within 5 seconds becomes `unknown/timeout`.

| Common code | Handling |
| --- | --- |
| `view_not_ready`, `action_unavailable` | Wait for the view/capability to become available and update the UI |
| `player_not_local`, `player_unavailable` | Retrieve the local body from a new view; do not reuse an invalidated object |
| `invalid_payload` | Correct the argument structure |
| `request_queue_full`, `transport_unavailable` | Clear UI waiting state and avoid unlimited automatic retries |
| `source_changed`, `stale_world` | The request's room/world has changed |
| `rate_limited`, `operation_busy` | Participant already has an operation or is still on cooldown |
| `action_disabled`, `owner_unavailable` | Host capability or initiating participant is no longer available |
| `timeout`, `handler_error`, `operation_error`, `operation_timeout`, `invalid_result_data` | Result is uncertain; inspect authoritative state |
| `request_id_reused`, `dedupe_expired`, `generation_limit` | Deduplication boundary; do not modify an old ID or automatically create a new ID for an unknown result |

Always inspect both `status` and `code`. World-reset reasons and business handlers may also provide codes. Invalid registration parameters, duplicate IDs, and invalid method calls are programming errors and throw Lua exceptions. An exception in a result callback is logged only.

## Auto-Adapter Management

`IsaacLAN:RegisterAdapter(definition)`, `GetAdapters()`, and `SetAdapterEnabled(id, enabled)` manage automatic compatibility modules. See the [Adapter Reference](https://github.com/BMingSY/isaac-lan/blob/main/docs/mod-adapter-development.md) for definitions, probing, cleanup, state, and persistent toggles.

`IsaacLAN:SetActionEnabled(id, name, enabled)` changes the toggle for an action registered locally; it is not persisted. It returns `true` on success or `false, "action_not_registered"` if the action does not exist. Whether the party can execute it is determined by the capability published by the host.
